# F1 — Agent Graph System and Foundation Kernel

## 1. Executive Summary

F1 closes the operational foundation plus the OCTO v5 **Agent Graph System**. The graph scope is explicit and limited: make `Agency → Department → Workspace → Agent` visible, persisted, guarded and operable through minimum CRUD and state projection.

F1 does **not** include real agent execution, runtime streaming, flow editing, SubAgent runtime orchestration or F2/F3 execution behavior. Runtime fields may be projected only as honest operational state; they must not be invented by the UI.

## 2. Definition of Done

F1 is COMPLETE only when all of these are true:

- foundation services build, deploy and report real health: API, PostgreSQL, Redis, LiteLLM gateway visibility and workers/queues where configured;
- the web console exposes the **F1 Agent Graph Console** at `/` and keeps foundation status available at `/status`;
- authenticated graph reads use server-side credentials or a session-aware backend path, not browser-public secrets;
- console writes go through the web backend route/session-aware proxy and then through `apps/api` JWT/RBAC/tenant/hierarchy guards;
- CRUD smoke covers `Agency → Department → Workspace → Agent` with persistence, patch, activation/archive, reparent and Agent delete;
- expected error paths are validated: missing credentials, invalid hierarchy, self-parent/cycle, invalid activation state and cross-tenant/nonexistent node access;
- `pnpm f1:close-gate` validates Agent Graph as F1 and does not print “F2 close” for this capability.


## Public surface contract

F1 has exactly one public-surface contract: **web + API**. The deployable F1 stack includes `apps/web` and `apps/api` together. The web service is the user-facing surface, while the API remains the backend surface under `/api/*`.

Required routes:

- `GET /` on the web origin renders the **F1 Agent Graph Console** and includes the stable `F1 · Agent Graph System` marker.
- `GET /status` on the web origin renders foundation/service status.
- `GET /api/health/live`, `GET /api/health/ready` and `GET /api/health/version` on the API origin validate API liveness, readiness and build metadata.
- `GET /api/v1/agents/*` and related Agent Graph write endpoints remain owned by `apps/api`; the web console reaches them through server-side calls or same-origin proxy routes.

Local compose defaults are `F1_WEB_URL=http://localhost:3000`, `API_ROOT_URL=http://localhost:3001` and `API_URL=http://localhost:3001/api`. Coolify deployments may use one compose resource or explicit web/API resources, but they must preserve the same contract: `/` is the Agent Graph Console, `/status` is web status, and `/api/*` is API. F1 is not API-only.

## 3. F1 Agent Graph Scope

Included in F1:

- persisted hierarchy levels: `Agency`, `Department`, `Workspace`, `Agent`;
- valid relationships: root `Agency`, `Agency → Department`, `Department → Workspace`, `Workspace → Agent`;
- `GET /api/v1/agents/graph` nested graph projection;
- `GET /api/v1/agents/nodes/:nodeId` node detail projection;
- `POST /api/v1/agents/nodes` for Agency/Department/Workspace creation;
- `POST /api/v1/agents` for Agent creation under a Workspace;
- `PATCH /api/v1/agents/nodes/:nodeId` for `name`, `slug`, `activationState`, `modelPolicy`, `toolPolicy`, `budgetPolicy`, `governance`, `capabilities`, `coreFiles` and `memoryPolicy`;
- `PATCH /api/v1/agents/:id` for Agent operational fields (`name`, `role`, `goal`, `status`, `capabilities`, policies and hierarchy parent) with linked hierarchy-node synchronization where applicable;
- `PATCH /api/v1/agents/nodes/:nodeId/parent` for backend-validated reparenting;
- archive as the destructive operation for non-Agent nodes via `activationState: archived`; physical deletion is only available for the selected Agent through `DELETE /api/v1/agents/:id`;
- effective policy/capability projection from the persisted chain;
- explicit `runtimeStatus: null`/unavailable when runtime projection does not exist.

### Operational CRUD contract

F1 treats the graph as Control Plane state, not as SaaS tenancy. API/service/repository code is authoritative for hierarchy and tenant invariants. The web console and proxy may filter obvious parent candidates for usability, but failed hierarchy decisions must come from the backend.

The only valid F1 edges are root `Agency`, `Agency → Department`, `Department → Workspace` and `Workspace → Agent`. Reparent operations are transactional and reject invalid parent levels, self-parent, descendant parents/cycles, missing parents and cross-tenant parents. When a Department, Workspace or Agent node moves, effective graph policy is recalculated from persisted ancestors at read time, and Agent scope metadata (`agencyId`, `workspaceId`) is synchronized for affected descendant Agents.

`activationState` is authoritative and limited to `active`, `inactive` and `archived`; `paused` is accepted as a control-plane alias and persisted/projected as `inactive`. Archiving a non-Agent node does not cascade delete descendants; it records the node state so descendants remain inspectable and the effective chain remains auditable. F1 does not implement physical deletion for non-Agent nodes because accidental subtree deletion is too risky for the minimum graph contract. Agent deletion removes the selected Agent and its linked Agent hierarchy node only.


### Effective policy and capability contract

F1 uses one read-time projection contract across repository, service, DTOs, UI and smoke tests:

- `toolPolicy.allow` and `toolPolicy.deny` are tool policy only. They are projected under `effectivePolicies.toolPolicy`; denied tools are removed from the effective allow list and remain visible in `deny` for audit.
- `capabilities` are declarative capabilities, not tools. Agency, Department, Workspace and linked Agent hierarchy nodes may declare inheritable `capabilities` as an array of strings.
- `agent.capabilities` is the Agent record's local capability list. It is appended after inherited hierarchy capabilities.
- `effectiveCapabilities` is the stable, deduplicated union in hierarchy order: `Agency → Department → Workspace → Agent hierarchy node → Agent record`.
- A more specific F1 level can add capabilities but cannot remove capabilities inherited from ancestors.
- Capability deny/override semantics and a larger `CapabilityProfile` model are intentionally out of scope for F1. If F2/F3 needs capability denial, it should introduce an explicit future contract such as `capabilityPolicy.deny` rather than mixing tool policy with capabilities.

## 4. Secure Console Model

The browser must never hold an OCTO write token through a `NEXT_PUBLIC_*` variable. The console uses a same-origin backend route at `apps/web/src/app/api/agent-graph/route.ts`:

- reads require server-side `OCTO_WEB_CONSOLE_TOKEN` and call `GET /api/v1/agents/graph` from the server through an `API_URL` base that already includes `/api`;
- writes require either an `httpOnly` `octo_console_token` session cookie or explicit development/smoke opt-in with `OCTO_WEB_CONSOLE_ALLOW_SERVER_TOKEN_WRITES=true` plus server-side `OCTO_WEB_CONSOLE_TOKEN`;
- the route only allows named Agent Graph actions and forwards them to the existing API endpoints, preserving backend JWT/RBAC/tenant/hierarchy guards.

Production deployments should prefer a real session cookie. The server-token write mode is for controlled internal/dev/smoke environments and must not be represented as a browser secret.

## 5. Out of Scope for F1

F1 does not include:

- real agent execution;
- streaming runtime responses;
- runtime status feeds beyond honest unavailable/null projections;
- visual DAG/flow editing;
- SubAgent runtime orchestration;
- durable tool calling beyond existing foundation contracts;
- semantic memory/RAG;
- external channels.

## 6. Validation

Use these commands for the graph slice and close gate:

- `pnpm --filter @octo/api test -- src/agents/agent-graph.integration.test.ts` validates service-level persistence and effective projections.
- `F1_WEB_URL=http://localhost:3000 API_URL=http://localhost:3001/api bash scripts/f1-smoke.sh --strict` validates the web Agent Graph Console at `/`, web foundation status at `/status`, API health/version metadata and foundation runtime evidence.
- `API_URL=http://localhost:3001/api pnpm f1:agent-graph-smoke` validates API-level CRUD, inherited capability projection, inherited tool allow/deny projection, node detail, patch, activation/archive, valid Department/Workspace/Agent reparent, invalid hierarchy/self-parent/cycle/missing-parent paths, cross-tenant rejection, Agent-node creation rejection through `/nodes` and selected Agent deletion against a local running API.
- `API_URL=https://agents.socialstudies.cloud/api pnpm f1:agent-graph-smoke` validates the same F1 graph contract against a deployed API.
- `pnpm f1:agent-graph-smoke` defaults to `API_URL=http://localhost:3001/api`, so all smoke calls target `/api/v1/agents/*`.
- `pnpm f1:verify` is a FAST local feedback command. It can emit explicit `F1 FAST WARNING: SKIP ...` warnings when DB/Redis or Docker are not available.
- `pnpm f1:runtime-handoff-smoke` validates runtime-worker `/health/live`, `/health/ready`, `/health/status`, `RUNTIME_DATABASE_URL` evidence, HTTP F1 handoff acceptance with `202 Accepted`, API runtime worker visibility and heartbeat evidence. In the close gate it runs from the host after `compose up`: HTTP uses published localhost ports, direct SQL heartbeat verification uses `F1_HOST_DATABASE_URL`, and Compose services/runtime-worker keep using `F1_COMPOSE_*` / `RUNTIME_DATABASE_URL` internally. It does not implement or require F2 DAG/streaming/multi-agent runtime features.
- `pnpm f1:close-gate` is the strict F1 close command. It allows no silent skips, blocks on build/typecheck, lint, unit tests, DB/Redis integration, tenant isolation, observability, migrations, compose build/up, runtime handoff/heartbeat smoke, public smoke, Agent Graph F1 smoke and runtime DB-role smoke.

The close command writes `docs/reports/f1-close-report.md` with UTC timestamps, commit, branch, gate command, environment, CI/deploy metadata, compose project, build metadata, verified URLs, per-check results, skip policy and final PASS/FAIL decision. It must not report PASS unless every required check passes; if a prerequisite stops the gate, unreached required checks are still recorded as FAIL/not-run. See `docs/f1-release-gate.md` for the canonical gate contract.

## 7. Runtime Worker database role closure

F1 keeps direct Runtime Worker writes to PostgreSQL only for durable execution progress. This avoids pretending F2/F3 persistence abstractions already exist while still enforcing least privilege in the current F1 model.

`apps/runtime-worker` must connect with `RUNTIME_DATABASE_URL` in F1 close and production deployments. `DATABASE_URL` is reserved for API, migrations and administrative bootstrap. Configure these runtime environment variables in local compose/Coolify; do not store real secrets in files:

| Variable | Purpose |
|---|---|
| `RUNTIME_POSTGRES_USER` | PostgreSQL login used only by Runtime Worker; default `octo_runtime`. |
| `RUNTIME_POSTGRES_PASSWORD` | Secret password for the runtime role; required by compose/bootstrap. |
| `RUNTIME_DATABASE_URL` | Runtime Worker DSN, for example `postgresql://${RUNTIME_POSTGRES_USER}:${RUNTIME_POSTGRES_PASSWORD}@postgres:5432/${POSTGRES_DB}` in compose/Coolify. |

The F1 runtime role allowlist is exactly: `approvals`, `execution_checkpoint_writes`, `execution_checkpoints`, `execution_steps`, `executions`, `outbox_events`, `tool_invocations`, `worker_heartbeats`. It may `SELECT`, `INSERT` and `UPDATE` these tables and may use schema `public`; it must not have DDL, migration-table access, `CREATE` on `public`, broad grants, `BYPASSRLS`, or administrative attributes.

Operational sequence for local/Coolify F1:

1. Run the canonical `migrate` service with privileged `DATABASE_URL` plus `RUNTIME_POSTGRES_PASSWORD`. `packages/database/src/migrate.ts` applies Drizzle migrations and then idempotently creates/updates `octo_runtime`, rotates the runtime password and validates effective privileges.
2. Use `scripts/bootstrap-runtime-db-role.sh` only as a manual fallback/rotation path when migrations are run outside the compose `migrate` service. The versioned SQL migration keeps the role/grant contract visible but does not contain a password because secrets must enter through environment variables only.
3. Start `runtime-worker` with `RUNTIME_DATABASE_URL`; do not inject `DATABASE_URL` into that service as its runtime credential.
4. Verify the DB role with `bash scripts/f1-runtime-db-role-smoke.sh --strict`.
5. Verify deployed runtime-worker status and F1 HTTP handoff acceptance with `pnpm f1:runtime-handoff-smoke` or the full `pnpm f1:close-gate`; when running from the host, pass `DATABASE_URL=$F1_HOST_DATABASE_URL` for direct heartbeat SQL checks and keep runtime-worker configured with `RUNTIME_DATABASE_URL`.

The smoke validates that the role can connect and perform required F1 progress writes inside tenant-scoped transactions, and that it cannot create/alter/drop tables, create temporary tables, read control-plane/migration tables, hold effective table privileges outside the F1 allowlist, or hold sequence privileges outside sequences owned by the F1 allowlist tables.

## Queue workers closure (#289)

La fundación F1 incluye tres procesos vivos de queue además de Redis: `scheduler-worker`, `reclaimer-worker` y `outbox-publisher-worker`. `/api/health/ready` puede demostrar conectividad API → Redis/BullMQ, pero no demuestra consumidores ni flujo durable end-to-end.

El criterio F1 de cierre es reproducible con `pnpm f1:queue-workers-smoke` y queda dentro de `pnpm f1:close-gate`. La prueba debe ejecutarse contra el stack Docker/Compose/Coolify completo y verifica:

- health/readiness de scheduler, reclaimer y outbox publisher;
- heartbeats frescos en `worker_heartbeats` para evitar falsos positivos con procesos muertos;
- dispatch durable: la ejecución nace en PostgreSQL, usa `queue_job_id = execution.id`, llega a `execution.dispatch` y el scheduler la consume;
- handoff F1 al runtime-worker por HTTP, sin declarar cerrado un motor F2;
- publicación outbox con eventos marcados/publicados, sin pérdida silenciosa;
- reclaim/retry de una ejecución running/zombie con lease expirado, sin duplicar efectos observables.

Redis sano por sí solo no cierra F1. F1 solo cierra cuando los workers están vivos y el flujo durable PostgreSQL → BullMQ → scheduler → runtime handoff → PostgreSQL/outbox → reclaim queda demostrado.
