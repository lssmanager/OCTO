F1 — Foundation Platform Kernel

## 1. Executive Summary

F1 es la fase de fundación operacional de OCTO. Su objetivo no es crear agentes completos ni ejecutar tareas reales de agente, sino demostrar que la plataforma base vive: despliega, responde, se conecta, se observa y expone una GUI mínima que muestra el estado real de los servicios.

F1 cierra cuando existe una URL pública de fase, una API funcional, una base de datos conectada, Redis conectado, LiteLLM visible como gateway, runtime-worker presente con health check, configuración validada, logs visibles y un dashboard mínimo capaz de indicar qué está online, qué está pendiente y qué está fallando.

El principio permanente para OCTO es: **cada fase debe cerrar con una GUI mínima verificable**, pero esa GUI solo debe mostrar la capacidad propia de la fase. En F1 la GUI no debe simular creación de agentes ni ejecución real; debe mostrar la salud y disponibilidad de la fundación.

## 2. Definition of Done

F1 se declara COMPLETE cuando se cumplen simultáneamente estas condiciones:

- URL pública de F1 respondiendo.
- GUI mínima `Foundation Status Dashboard` cargando correctamente.
- API con endpoints `live` y `ready` funcionales.
- PostgreSQL conectado y reportado en la GUI.
- Redis conectado y reportado en la GUI.
- LiteLLM configurado o conectado y reportado en la GUI.
- Runtime-worker presente y reportando health.
- Scheduler-worker, reclaimer-worker y outbox-publisher-worker visibles como `online`, `pending` o `not configured`, sin falsos verdes.
- Docker Compose deployable.
- Variables de entorno obligatorias validadas al startup.
- Logs visibles en Coolify o entorno equivalente.
- Build phase, versión, environment y último health check visibles.
- Smoke test mínimo verificando GUI + API + servicios base.

## 3. GUI mínima obligatoria

La GUI de cierre F1 es un dashboard de fundación, no una consola de agentes.

Ejemplo esperado:

```txt
OCTO FOUNDATION — F1

API                  Online
PostgreSQL           Connected
Redis                Connected
LiteLLM              Connected
Runtime Worker       Online
Scheduler Worker     Online / Pending
Reclaimer Worker     Online / Pending
Outbox Publisher     Online / Pending

Build Phase          F1
Environment          staging
Last Health Check    ok
```

Estados permitidos:

- `Online`: el servicio responde y está listo.
- `Connected`: la dependencia responde desde la API o servicio responsable.
- `Pending`: el componente existe en el roadmap o compose, pero todavía no es requisito funcional de la fase.
- `Not configured`: falta configuración requerida.
- `Offline`: el componente debería estar disponible, pero no responde.

La GUI debe ser honesta. Un componente pendiente no debe mostrarse como verde.

## 4. Alcance incluido

F1 incluye:

- monorepo y build base;
- Docker Compose deployable;
- preparación para Coolify;
- API base;
- PostgreSQL;
- Redis;
- LiteLLM gateway visible;
- runtime-worker con health check;
- scheduler/reclaimer/outbox visibles como estado operativo o pendiente;
- sistema de env vars y secret management básico;
- health checks;
- logs;
- dashboard mínimo;
- smoke test de fundación.

## 5. Fuera de alcance

F1 no incluye:

- crear agentes desde la GUI;
- crear relaciones jerárquicas;
- Agent Graph navegable;
- ejecución real de tareas de agente;
- tool calling durable;
- checkpoint/reclaim avanzado;
- timeline avanzado de ejecuciones;
- flow editor;
- memoria semántica/RAG;
- canales externos;
- multi-agent orchestration.

Estas capacidades se abren en fases posteriores cuando la fundación ya está viva y verificable.

## 6. Secuencia posterior recomendada

La secuencia canónica posterior queda así:

| Fase | Capacidad principal | GUI mínima de cierre |
|---|---|---|
| F1 | Foundation Platform Kernel | Dashboard de servicios base |
| F2 | Agent Registry & Hierarchy | Árbol/grafo mínimo Agency → Agent |
| F3 | First Real Agent Execution | Crear agente simple y ejecutar una tarea básica |
| F4 | Durable Runtime | Timeline, checkpoints, reclaim y recovery visibles |
| F5 | Tools & Policies | Tool registry, permissions y approvals básicos |
| F6 | Channels | Estado y prueba mínima de canal conectado |
| F7 | Memory/RAG | Estado de Qdrant, embeddings y retrieval test |
| F8 | Planner/DAG | DAG mínimo visible y ejecutable |
| F9 | AI Operating System | Plataforma integrada completa |

## 7. Validaciones técnicas

Validaciones mínimas para F1:

| Validación | Resultado esperado |
|---|---|
| `docker compose up` levanta servicios base | Sí |
| API `/health/live` responde | Sí |
| API `/health/ready` responde | Sí |
| DB health desde API | Connected |
| Redis health desde API | Connected |
| LiteLLM health/config desde API o dashboard | Visible |
| Runtime-worker health | Online |
| GUI F1 carga desde URL pública | Sí |
| Dashboard muestra estados reales | Sí |
| Logs visibles en entorno de despliegue | Sí |
| Variables críticas faltantes fallan explícitamente | Sí |

## 8. Criterios de estabilidad

F1 STABLE no requiere agentes ejecutando tareas. Requiere estabilidad de la fundación:

- API y dashboard disponibles durante una ventana definida.
- Health checks sin falsos positivos.
- DB y Redis conectados de forma sostenida.
- Runtime-worker sin crash loop.
- Logs suficientes para diagnosticar caída de servicio base.
- Deploy reproducible.
- Rollback básico documentado.

## 9. Principio permanente de cierre de fases

Cada fase de OCTO debe cerrar con:

- URL pública o ambiente accesible;
- GUI mínima específica de la fase;
- backend funcional para esa capacidad;
- health checks;
- persistencia o estado real cuando aplique;
- logs visibles;
- smoke test;
- criterios de pendiente/fallo explícitos.

La GUI mínima no debe adelantar capacidades de fases futuras. Debe probar visualmente solo lo que esa fase promete cerrar.

## 10. Decisión arquitectónica

F1 se redefine como fundación operacional. La creación de agentes, el Agent Graph y la ejecución real se mueven a fases posteriores.

Esta decisión evita cerrar F1 con una demo prematura que mezcle jerarquía, runtime, tools, checkpoints y políticas antes de tener la plataforma base desplegada y observable.
