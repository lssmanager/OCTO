F1 — Core Runtime & Real Agent Execution
1. Executive Summary
F1 habilita la primera versión real de OCTO como sistema de ejecución agentic durable, con separación estricta entre Control Plane en NestJS y Execution Plane en workers aislados de Python, usando PostgreSQL como system of record, Redis/BullMQ para coordinación y LiteLLM como gateway único de inferencia detrás de una capa de abstracción de providers.

F1 resuelve el principal gap dejado por F0: el sistema ya no solo define contratos, colas, observabilidad y bases de persistencia, sino que ejecuta agentes reales, persiste checkpoints recuperables, reintenta trabajos, recupera ejecuciones zombie, expone APIs operables y aplica aislamiento por tenant sin mezclar tenancy con la jerarquía cognitiva Agency/Department/Workspace/Agent/SubAgent.

F1 introduce los siguientes componentes netos: ExecutionController, AgentController, RuntimeController, OpsController, ExecutionDispatcher, ExecutionLeaseService, CheckpointService, ToolRegistry, LiteLLMAdapter, RedisStreamEventBus, JWTAuthModule, políticas RLS en PostgreSQL, sincronización de contratos TS/Python y una suite de integración con Postgres+Redis reales en CI.

F1 endurece componentes existentes de F0: FSM con CAS, DLQ, idempotencia, lease/reclaim, contratos compartidos, observabilidad OTel, estrategia Docker multi-stage y validación estricta de configuración al startup.

F1 complete significa que un request autenticado puede crear o seleccionar un agente, iniciar una ejecución durable, despacharla a un runtime-worker aislado, ejecutar una o más llamadas LiteLLM, ejecutar tools permitidas, persistir cada transición y checkpoint en PostgreSQL, publicar eventos operativos, recuperarse tras caída del worker y entregar resultado final o fallo terminal sin pérdida de consistencia observable.

Production-ready for F1 significa single-region operable con health checks, migrations zero-downtime, alertas mínimas, métricas de reclaim/replay, RLS activa, JWT validado, idempotencia operativa, imágenes endurecidas, CI obligatoria y recuperación comprobada ante restart de contenedores y expiración de lease.

Non-goals de F1 son memoria semántica/RAG completa, channels reales de mensajería, multi-agent orchestration avanzada, flow engine visual, A2A distribuido full, evaluación automática, browser automation y enterprise scale features como SSO/SCIM/billing, porque el roadmap oficial exige estabilizar primero el kernel durable y la ejecución base antes de abrir capas superiores.

2. Architecture Overview
La arquitectura F1 conserva la separación obligatoria de 10 capas de OCTO y materializa la regla de que el runtime nunca vive en API, frontend ni WebSocket layer, sino en workers aislados con sus propias colas, recursos y límites de seguridad.

El Control Plane conserva autoridad sobre auth, CRUD, scheduling, governance, políticas, persistencia y coordinación; el Execution Plane solo ejecuta runs, LLM calls, tool calls, checkpoints, retries, pause/resume y publicación de eventos de runtime.

Boundary durable F1: aunque la autoridad funcional anterior se mantiene, el runtime-worker F1 es un escritor directo y explícito de PostgreSQL para progreso durable. Su `DATABASE_URL` es requisito de ejecución. Las escrituras permitidas se limitan a `executions`, `execution_steps`, `execution_checkpoints`, `execution_checkpoint_writes`, `tool_invocations`, `approvals`, `outbox_events` y `worker_heartbeats`. Esta decisión pragmática cierra F1 sin bloquear recuperación/reclaim, pero queda registrada como deuda aceptada: F2+ debe moverla a event-sourcing, una API interna del Control Plane o un adapter de persistencia abstracto que preserve commits atómicos de estado + outbox, FSM/CAS y replay de checkpoints.

2.3 Queue topology
text
execution.dispatch      -> scheduler-worker     -> HTTP 202 runtime handoff
execution.retry         -> scheduler-worker     -> HTTP 202 runtime handoff
execution.reclaim       -> scheduler-worker     -> HTTP 202 runtime handoff
execution.cancel        -> runtime-worker       -> terminal transition
execution.resume        -> scheduler-worker     -> HTTP 202 runtime handoff
tool.async.result       -> runtime-worker       -> continue checkpoint
ops.dlq.reprocess       -> ops worker/manual    -> replay guarded
BullMQ se usa para comandos de trabajo con reintentos, backoff y DLQ; Redis Streams se usa para eventos consumibles por UI, Ops y auditores, porque los comandos requieren semántica de ejecución/retry mientras los eventos requieren fan-out y replay temporal.

Esta separación evita convertir el event bus en un scheduler implícito y preserva el principio de responsabilidades explícitas entre orquestación y timeline observable.

En F1 el consumidor primario documentado de `execution.dispatch` es `scheduler-worker`: su rol operativo es scheduler + dispatcher HTTP. El runtime-worker no consume BullMQ directamente en esta fase; acepta handoffs internos por HTTP 202 y ejecuta el loop durable fuera del ciclo de vida del request.

2.4 Durable execution flow
text
Client -> API POST /executions
  -> DB insert execution(state=QUEUED, version=0)
  -> DB insert outbox_event(ExecutionQueued)
  -> BullMQ add execution.dispatch(jobId=execution_id)

scheduler-worker
  -> lock execution row CAS QUEUED->DISPATCHED
  -> assign lease_owner + lease_expires_at
  -> HTTP POST /api/v1/execute with bounded handoff timeout
  -> BullMQ retries only until runtime returns 202 Accepted

runtime-worker
  -> return 202 Accepted without waiting for completion
  -> start asynchronous runtime task
  -> CAS DISPATCHED->RUNNING
  -> create checkpoint(step=0, source=input)
  -> LLM/tool loop
  -> after every state transition: step row + checkpoint + outbox_event
  -> on success CAS RUNNING->SUCCEEDED
  -> on terminal failure CAS RUNNING->FAILED
La semántica durable sigue el patrón LangGraph de checkpointing persistente y writes intermedios separados, con cada transición materializada en DB y no solo en memoria del proceso, de modo que pause/resume, replay y recovery sobreviven reinicios completos del worker.

La regla operacional es que todo paso observable del runtime debe dejar rastro persistente en execution_steps, execution_checkpoints y outbox_events antes de liberar control al siguiente paso.

2.5 Retry/reclaim flow
text
RUNNING execution
  -> worker heartbeat stops
  -> lease_expires_at passes
  -> scheduler scans stale leases
  -> CAS RUNNING->RECLAIMING if lease_owner matches stale owner
  -> enqueue execution.reclaim
  -> new worker loads last valid checkpoint
  -> CAS RECLAIMING->RUNNING
  -> continue from checkpoint_id
  -> if max_reclaims exceeded -> FAILED + DLQ
El reclaim no recrea ejecución desde cero; reanuda desde el último checkpoint consistente confirmado en PostgreSQL, siguiendo el contrato durable derivado de LangGraph y las reglas de lease/reclaim ya fundadas en F0.

Los mensajes venenosos o corrupciones repetidas se enrutan a DLQ después del umbral configurado de retries y reclaims para evitar loops infinitos y explosión de costos.

2.6 Tool execution flow
text
runtime-worker
  -> model returns tool_calls[]
  -> ToolRegistry resolves tool definition
  -> PolicyEngine validates tenant + agent + tool permission
  -> ToolInvocation row inserted(status=PENDING)
  -> execute sync tool OR dispatch async tool
  -> capture stdout/stderr/result/schema validation
  -> persist ToolInvocation(status=SUCCEEDED|FAILED|TIMED_OUT)
  -> append checkpoint write
  -> continue LLM loop
El runtime trata cada tool call como un paso durable y auditable con permisos explícitos, timeout, validación de esquema y registro operativo, en línea con la exigencia arquitectónica de sandboxing, audit logging y límites por tool para prevenir prompt injection, tool poisoning y exfiltration.

La compatibilidad MCP entra como un adaptador de tools y no como un bypass del runtime principal, preservando contratos únicos de ejecución y observabilidad.

2.7 Auth flow
text
User -> POST /auth/login
  -> JWT access token (tenant_id, subject, roles, scopes)

User -> POST /executions
  -> NestJS JwtAuthGuard validates signature + expiry
  -> TenantScopeGuard injects tenant_id
  -> Service sets SET LOCAL app.current_tenant = :tenant_id
  -> DB RLS filters visible rows
  -> execution created with tenant_id
La jerarquía cognitiva sigue perteneciendo a agent-core y no a auth; tenancy existe como frontera de seguridad y ownership de datos, no como modelo conceptual del grafo de agentes.

Toda request debe validar identity, permissions, scope, origin e integrity, conforme al modelo zero-trust descrito en la arquitectura oficial.

2.8 Event propagation flow
text
runtime-worker -> outbox_events(insert)
               -> tx commit
               -> outbox publisher
               -> Redis Stream octo.events
               -> API WS/SSE gateway
               -> Web UI timeline / ops dashboard / audit consumers
El evento nunca se publica directamente antes del commit de base de datos; se publica desde outbox para evitar eventos fantasma sin estado durable asociado y para soportar replay de propagación sin duplicar efectos de negocio.

3.3 Scope invariants
Un execution run en F1 pertenece a un solo tenant_id y a un solo agent_id raíz.

Un run puede reanudarse únicamente desde checkpoints validados y no desde estado reconstruido heurísticamente en memoria.

Un tool call no puede saltarse ToolRegistry, PolicyEngine, ToolInvocation ni observabilidad estructurada.

El frontend nunca decide transiciones del runtime; solo proyecta estado y envía comandos autorizados al Control Plane.

PostgreSQL es la autoridad duradera; Redis nunca es fuente primaria de verdad.

4. Runtime Execution Engine
4.1 Engine lifecycle
El lifecycle del engine es QUEUED -> DISPATCHED -> RUNNING -> {PAUSED|SUCCEEDED|FAILED|CANCELLED} con estados operativos auxiliares RETRY_SCHEDULED, RECLAIMING, TIMED_OUT y DLQ, todos controlados por CAS sobre la fila de executions.

Cada transición se valida por versión (version) y estado anterior esperado, de forma que dos workers nunca puedan confirmar el mismo avance lógico del run.

4.2 FSM states
State	Meaning	Entered by	Exit conditions
QUEUED	Run creado, no despachado.	API create execution.	DISPATCHED, CANCELLED.
DISPATCHED	Scheduler asignó intento y lease inicial.	scheduler-worker.	RUNNING, FAILED.
RUNNING	runtime-worker ejecutando loop activo.	runtime-worker.	PAUSED, SUCCEEDED, FAILED, TIMED_OUT, RECLAIMING, CANCELLED.
PAUSED	Espera durable por aprobación o input externo.	runtime-worker.	RUNNING, CANCELLED, FAILED.
RETRY_SCHEDULED	Falla recuperable con nuevo intento diferido.	runtime-worker/scheduler.	DISPATCHED, FAILED.
RECLAIMING	Lease venció y otro worker toma control.	scheduler-worker.	RUNNING, FAILED.
TIMED_OUT	Runtime superó timeout total de ejecución.	scheduler-worker / watchdog.	terminal.
SUCCEEDED	Resultado final persistido.	runtime-worker.	terminal.
FAILED	Error terminal no recuperable.	runtime-worker / scheduler.	terminal.
CANCELLED	Usuario u operador abortó el run.	API / runtime.	terminal.
DLQ	Job desviado por envenenamiento operacional.	scheduler-worker.	QUEUED manual only.
Esta máquina de estados amplía el patrón LangGraph INIT/RUNNING/PAUSED/FAILED/COMPLETED/CANCELLED con estados operativos exigidos por cola distribuida y reclaim productivo.

La semántica es estricta: un estado terminal nunca vuelve a no terminal, y PAUSED solo reanuda mediante señal explícita durable con evidencia persistida.

From	Event	To	Persistence action

4.4 CAS semantics
sql
UPDATE executions
SET state = $next_state,
    version = version + 1,
    updated_at = now(),
    lease_owner = $lease_owner,
    lease_expires_at = $lease_expires_at
WHERE id = $execution_id
  AND tenant_id = $tenant_id
  AND state = $expected_state
  AND version = $expected_version;
El resultado esperado es row_count = 1; cualquier otro valor significa race, stale worker o comando duplicado y se trata como no-op operacional con log estructurado cas_conflict=true.

CAS es obligatorio porque el runtime es distribuido, BullMQ puede redespachar y el reclaim implica cambio de ownership entre procesos distintos.

4.5 Dispatch pipeline
POST /executions valida JWT, scope y pertenencia del agent_id al tenant.

API crea execution, execution_step(type=CREATED) y outbox_event(ExecutionQueued) en una sola transacción.

API encola job execution.dispatch con jobId = execution_id para garantizar idempotencia de encolado.

scheduler-worker toma el job, hace CAS QUEUED -> DISPATCHED, asigna lease y encola runtime.execute.

runtime-worker hace CAS DISPATCHED -> RUNNING, compila contexto y crea checkpoint inicial.

4.6 Execution pipeline
Resolver ExecutionContext efectivo desde Agency/Department/Workspace/Agent, sin mezclar jerarquía cognitiva con tenancy.

Cargar model routing, policy de budget, tools permitidas y timeout total.

Persistir checkpoint(step=0, source=input).

Ejecutar loop: LLM -> parse tool calls -> tool execution -> append tool results -> next LLM call hasta alcanzar final_output o terminal error.

Después de cada step, persistir execution_step, checkpoint, métricas y evento outbox antes de continuar.

4.7 Retry semantics
Los retries se clasifican en provider_retry, tool_retry, runtime_retry y dispatch_retry, con contadores independientes para evitar que una falla transitoria de provider consuma el presupuesto de reclaim del execution completo.

La política por defecto es exponential backoff con jitter: 2s, 10s, 30s para errores transitorios de LiteLLM y 5s, 20s para tools HTTP/stdio recuperables; al superar el umbral se transiciona a FAILED o DLQ según tipo de error.

json
{
  "retryPolicy": {
    "provider": { "maxAttempts": 3, "backoffMs": [2000, 10000, 30000] },
    "tool": { "maxAttempts": 2, "backoffMs": [5000, 20000] },
    "runtime": { "maxAttempts": 2, "backoffMs": [1000, 5000] },
    "reclaim": { "maxAttempts": 3 }
  }
}
4.8 Timeout semantics
dispatch_timeout_ms = 30000.

runtime_start_timeout_ms = 60000.

llm_call_timeout_ms = 90000.

tool_call_timeout_ms = 30000 para sync y async_result_ttl_ms = 900000 para async.

execution_total_timeout_ms = 900000 por defecto, configurable por agent policy heredada.

Un timeout parcial no mata necesariamente el run; primero se evalúa retry policy y budget restante, y solo cuando el timeout afecta el límite total o excede los intentos permitidos se emite fallo terminal.

4.9 Cancellation semantics
La cancelación es cooperativa y durable: API marca cancel_requested_at, emite comando execution.cancel y el worker verifica la marca al inicio de cada step boundary y antes de invocar LiteLLM o tools.

Si el run está en PAUSED, la cancelación salta directo a CANCELLED; si está dentro de una llamada no interrumpible, se marca cancellation_pending=true y se aplica en el siguiente boundary seguro.

4.10 Resume semantics
Resume solo existe para PAUSED y RECLAIMING; nunca para FAILED, TIMED_OUT o DLQ sin intervención operatoria explícita.

El worker reanuda cargando CheckpointTuple más reciente válido, sus pendingWrites y el resume token derivado del approval o del reclaim event.

4.11 Determinism rules
El orden de messages[], tool results[] y checkpoint_writes[] se conserva por step_index y write_index monotónicos.

Los timestamps no participan en lógica de replay; el replay usa checkpoint_id, step_index y write_index.

El resultado de herramientas no determinísticas debe persistirse completo para que el replay no reejecute side effects externos.

La compilación de contexto efectiva se snapshottea en execution_context_snapshot al inicio del run para impedir drift por cambios del agente durante la ejecución.

4.13 Failure model
Failure type	Detection	Recovery	Terminal condition
Worker crash	heartbeat loss / lease expiry	reclaim from last checkpoint	reclaim attempts exhausted
LiteLLM 5xx	adapter error mapping	provider retry/backoff	attempts exhausted
Tool timeout	local timer	tool retry if safe	unsafe side effect or attempts exhausted
CAS conflict	update rowcount=0	no-op/log/reload state	repeated stale ownership
DB transient error	SQLSTATE class 08 / 40	runtime retry	repeated tx failure
Corrupt checkpoint	schema validation fail	fallback to previous valid checkpoint	no valid checkpoint
Approval timeout	timeoutAt reached	reject/expire policy	policy terminal reject
DLQ poison	repeated invariant breach	operator inspection	manual replay only
4.14 Poison messages, zombie reclaiming, DLQ routing
Un job se considera poison cuando falla por la misma firma de error terminal o invariant breach tres veces consecutivas con el mismo execution_id, step_index y checkpoint_id; en ese punto pasa a DLQ y se bloquea replay automático.

Un run se considera zombie cuando su estado es RUNNING pero lease_expires_at < now() y no existe heartbeat fresco; el scheduler hace CAS a RECLAIMING, nunca directamente a RUNNING, para que el cambio de ownership quede auditado.

5. LiteLLM Integration
5.1 Architectural position
LiteLLM se integra exclusivamente detrás de la Provider Abstraction Layer, porque OCTO prohíbe dependencia directa del core con SDKs externos y exige que el routing por modelo, fallback chain y provider specifics se encapsulen en adapters estables.

El runtime invoca una interfaz canónica LLMProvider, y solo el adapter conoce la forma concreta del payload hacia LiteLLM.

5.2 Request flow
text
runtime-worker
  -> resolve effective model policy from hierarchy snapshot
  -> build canonical chat request
  -> attach tenant budget + trace metadata

La resolución de modelo debe respetar herencia Agency/Department/Workspace/Agent, donde el nivel más específico tiene prioridad y la fallback chain puede definirse por nivel jerárquico.

El tenant_id y execution_id se adjuntan como metadata en cada request para cost tracking, trazabilidad y enforcement de presupuestos.

5.6 Streaming
F1 soporta streaming solo entre runtime-worker y LiteLLM, y lo utiliza para early token accounting y logs de progreso, pero la respuesta al cliente externo se consolida como resultado final o stream SSE opcional desde API sin permitir que UI controle la lógica del run.

Los chunks de streaming no son source of truth; el único resultado durable es el assistant_message consolidado persistido al cierre del step.

5.7 Token accounting and budget governance
El runtime persiste input_tokens, output_tokens, total_tokens, estimated_cost_usd, provider, model y budget_policy_snapshot por step para que costo y trazabilidad queden ligados al checkpoint y al timeline.

El presupuesto se evalúa antes y después de cada llamada LLM; si el presupuesto restante no cubre el min_reserved_cost del siguiente step, el run entra a PAUSED con approval de override o falla con BUDGET_EXCEEDED según policy del agente.

5.8 Timeout policy, retries, rate limits, circuit breaker
Timeout por request: 90s default, override por agent policy.

Retries transitorios: 3 con backoff exponencial.

Rate limit local: token bucket por tenant_id + model en Redis.

Circuit breaker: abre tras 5 fallos consecutivos por provider:model en 60s; semiclosed a los 30s.

Fallback chain: agent override > workspace > department > agency > global default.

5.9 Observability fields
Cada llamada LiteLLM debe emitir atributos OTel y logs estructurados: tenant_id, execution_id, agent_id, provider, model, latency_ms, input_tokens, output_tokens, retry_count, fallback_level, circuit_state, http_status.

6. Tool Execution System
6.1 System definition
El sistema de tools de F1 es un subsistema runtime-first con registry explícito, contratos de entrada/salida basados en JSON Schema, permisos por tenant/agent, timeout y auditoría integral por invocación.

Ningún tool se invoca por nombre libre desde el modelo; el runtime solo ejecuta definiciones registradas y autorizadas por ToolRegistry y PolicyEngine.

6.3 Tool lifecycle
text
MODEL_TOOL_CALL_DETECTED
  -> TOOL_VALIDATED
  -> TOOL_AUTHORIZED

  -> TOOL_EXECUTING
  -> TOOL_RESULT_VALIDATED
  -> TOOL_CHECKPOINTED

Cada transición produce una fila en tool_invocations y un execution_step(type=TOOL_CALL) o TOOL_RESULT, permitiendo auditar exactamente qué tool pidió el modelo, con qué argumentos normalizados y qué salida produjo el runtime.

La validación de inputSchema ocurre antes de ejecutar; la validación de outputSchema ocurre antes de reinyectar el resultado al modelo.

6.4 Sync vs async tools
Sync tools se ejecutan dentro de la ventana del step actual y deben completar antes del siguiente LLM call.

Async tools insertan tool_invocations(status=PENDING_ASYNC) y el runtime pausa o espera evento de resultado, según policy del tool.

Un async tool nunca bloquea un thread in-memory; la espera siempre es durable vía DB + event bus.

6.5 Tool sandboxing
El documento arquitectónico exige sandboxing, timeout, rate limits, output validation y permission boundaries para todas las tools, por lo que F1 ejecuta builtin tools en subprocessos aislados del runtime principal y prohíbe acceso directo a filesystem host, Docker socket, secrets globales y raw DB connections fuera de adapters controlados.

Las tools de side effect alto requieren requiresApproval=true y no pueden ejecutarse automáticamente por defecto.

6.6 MCP compatibility
MCP entra en F1 como source of tools, no como plano paralelo de ejecución; el runtime resuelve una tool mcp_stdio o mcp_http, negocia tools/list, ejecuta tools/call, valida JSON Schema y persiste la invocación con el mismo contrato que cualquier tool builtin.

Las approval policies always_require, never_require, policy_based definidas en el ADR MCP se materializan en requiresApproval resuelto por policy efectiva del agente/tenant.

6.7 Compensation model
F1 aplica modelo de compensación solo para herramientas declaradas sideEffectLevel=high; estas tools deben registrar compensationAction o marcarse non_compensatable=true en la definición, de modo que Ops sepa si un fallo posterior admite rollback operativo.

El runtime no inventa compensaciones; solo ejecuta compensaciones explícitamente declaradas y autorizadas.

6.8 Retry, timeout and permissions
Tools retryable=true solo se reintentan si sideEffectLevel=none o si tienen idempotency key verificable.

Cada tool call genera idempotency_key = sha256(execution_id + step_index + tool_name + normalized_args).

El timeout es hard limit por proceso y soft limit por policy del execution.

La evaluación de permisos combina tenant_id, agent policy, tool allowlist, role, requiresApproval y scope.

6.9 Tool observability and audit trail
Toda invocación registra tool_name, kind, tenant_id, execution_id, arguments_hash, duration_ms, stdout_size, stderr_size, exit_code, approval_id, result_schema_valid, retry_count y trace_id.

La salida bruta puede truncarse para logs, pero el resultado validado persistido para replay debe mantenerse íntegro si el tool participa en determinismo del run.

7. Durable Execution
7.1 Responsibilities: PostgreSQL vs Redis
PostgreSQL guarda executions, execution_steps, execution_checkpoints, checkpoint_writes, tool_invocations, approvals, outbox_events, leases embebidas y audit trails porque es el system of record oficial.

Redis guarda colas BullMQ, streams de eventos, rate limits, heartbeats efímeros y caches transitorias porque no tiene autoridad duradera sobre el estado del run.

7.2 Resumability guarantees
El sistema garantiza resume-from-last-valid-checkpoint, no resume-from-last-instruction-pointer, porque la unidad de recuperación durable es el checkpoint persistido y validado, no el stack frame interno del worker caído.

Por lo tanto, un step en progreso que no alcanzó commit se reejecuta; un step ya checkpointed no se reejecuta salvo replay operatorio explícito.

7.3 Idempotency guarantees
F1 ofrece at-least-once execution a nivel de job de cola y effectively-once state transition a nivel de DB mediante CAS, idempotency keys y checkpointing.

No ofrece exactly-once distribuido end-to-end sobre side effects externos, por lo que las tools con side effects deben ser idempotentes o requerir aprobación y compensación explícita.

7.4 Lease model
text
lease_owner         = worker instance id
lease_version       = monotonically increasing integer
lease_expires_at    = timestamp
heartbeat_interval  = 10s
lease_duration      = 30s
stale_after         = now > lease_expires_at
El worker renueva lease en cada step boundary y cada 10 segundos durante operaciones largas, dejando rastro en DB y heartbeat efímero en Redis para diagnósticos rápidos.

Solo el owner vigente puede confirmar checkpoints nuevos; si pierde CAS por expiración o reclaim, debe abortar localmente.

7.5 Recovery algorithm
Scheduler detecta run stale por lease_expires_at.

Hace CAS RUNNING -> RECLAIMING con incremento de versión.

Encola execution.reclaim con nuevo lease owner.

Nuevo worker carga el último checkpoint válido y verifica integridad del lineage parent_checkpoint_id.

Si la validación pasa, crea execution_step(type=RECLAIMED) y CAS RECLAIMING -> RUNNING.

Continúa desde next_step_index.

Si no existe checkpoint válido, falla terminal con código CHECKPOINT_RECOVERY_FAILED.

7.8 Crash recovery scenarios
API restart no afecta runs activos porque el runtime vive fuera del proceso API.

runtime-worker restart se recupera por lease expiry + reclaim desde checkpoint.

scheduler restart no invalida estado porque la fuente de verdad está en DB y BullMQ persiste jobs en Redis.

Redis restart con AOF habilitado recupera colas y streams; si se pierde job, el reconciler de DB reencola QUEUED, DISPATCHED, RETRY_SCHEDULED y RECLAIMING inconsistentes.

PostgreSQL restart pausa nuevas transiciones; los workers deben fail-fast, soltar lease por expiración y permitir reclaim cuando DB vuelva.

8. Multi-Tenant Security
8.1 Security model
F1 implementa tenancy como frontera de seguridad y ownership de datos, manteniendo separada la jerarquía cognitiva de agentes que pertenece a agent-core y no al módulo auth.

El modelo es zero-trust: toda request valida identidad, firma, expiración, tenant, scopes, ownership y permisos antes de tocar estado durable.

10. Event Bus
10.1 Responsibilities split
BullMQ maneja comandos y unidades de ejecución con retry/backoff/DLQ; Redis Streams maneja eventos de dominio y runtime con fan-out, replay corto y consumo por múltiples subscribers.

Esta separación impide que eventos UI se conviertan en mecanismo implícito de control de estado y mantiene trazabilidad limpia entre command processing y event projection.

10.3 Delivery semantics and ordering
Ordering guarantee: total order por execution_id usando sequence monotónico.

Delivery guarantee: at-least-once en Streams; los consumers deben ser idempotentes.

Replay strategy: replay desde outbox_events en PostgreSQL para reconstrucción fuerte, y desde Streams solo para consumidores near-real-time.

Dead-letter events: eventos que no pueden publicarse desde outbox se reintentan y luego pasan a outbox_publish_dlq.

10.4 Tracing propagation
Cada evento propaga trace_id, span_id, tenant_id, execution_id y run attempt para correlación end-to-end entre API, scheduler, runtime y UI timeline.

## F1 close-gate verification (issue #171)

F1 now has two explicit verification paths:

- `pnpm f1:verify` runs the developer fast path (`scripts/f1-verify.sh --fast`). It keeps lint, typecheck, API unit tests, scheduler build, runtime-worker unit tests and the anti-stub gate. It may skip integration or Docker smoke only when local infrastructure is missing, and the skip is printed explicitly so it cannot be mistaken for F1 closure evidence.
- `pnpm f1:close-gate` runs the strict close gate (`scripts/f1-verify.sh --close`). This mode requires Docker Compose, starts real PostgreSQL and Redis, runs migrations, executes integration tests with real infrastructure, builds and starts the full compose stack, then runs `scripts/f1-smoke.sh --strict`. Close mode does not silently skip Docker, database, Redis, workers, migrations, integration tests or smoke evidence.

The strict smoke validates F1 COMPLETE behavior rather than only health checks. It waits for API, runtime-worker, scheduler-worker, outbox-publisher-worker and reclaimer-worker readiness; seeds a deterministic tenant agent/version in PostgreSQL; creates an execution through the Control Plane API; lets the dispatch queue and scheduler-worker invoke the runtime-worker; and verifies a durable terminal state in PostgreSQL. It then checks observable evidence for checkpoints, checkpoint writes from a real tool call, completed tool invocation rows, required timeline/outbox events, published outbox rows and Redis stream publication.

The strict smoke also seeds a minimal expired `running` execution and verifies that the reclaimer-worker detects it, transitions/requeues it through the scheduler-worker, and that the runtime-worker completes the reclaimed replay with published reclaim events. This validates the minimum F1 COMPLETE recovery path; it is not a substitute for the longer F1 STABLE/PRODUCTION READY soak, restart and seven-day stability criteria.

The close gate uses deterministic fake LLM mode (`OCTO_TEST_LLM_FAKE=tool_echo`) so CI needs no external provider secrets, but it does not bypass the canonical runtime-worker or dispatch path. The API still creates the execution, Redis/BullMQ carries the dispatch, scheduler-worker calls `/api/v1/execute`, runtime-worker writes durable state/checkpoints to PostgreSQL, and outbox-publisher-worker publishes post-commit events.

## F1 reclaim lease ownership contract (issue #172)

F1 reclaim now treats PostgreSQL as the source of truth for execution ownership. Every scheduler dispatch or reclaim replay assigns a fresh `lease_token` on the execution row alongside `lease_owner`, `worker_id`, `lease_expires_at`, `attempt` and `attempt_count`; that token and attempt are propagated to the runtime invocation. The effective owner for a runtime write is therefore the tuple `(tenant_id, execution_id, attempt, lease_owner, lease_token)`.

The runtime-worker must present the same `lease_token` and `attempt` before it can transition `dispatched -> running`, write significant replay/checkpoint progress, or persist terminal `completed`/`failed` state and terminal outbox events. A stale runtime that lost ownership returns `lost_ownership`/`STALE_OWNERSHIP` and does not emit terminal success/failure events.

The reclaimer invalidates expired running ownership atomically when it transitions `running -> reclaimable`: it clears `lease_owner`, `lease_token`, `worker_id` and `lease_expires_at`, increments `reclaim_count`, and requeues replay with reason `reclaim_replay`. When `maxReclaimAttempts` is exceeded, the execution is failed durably with reason `RECLAIM_MAX_ATTEMPTS_EXCEEDED`, an `ExecutionFailed` outbox event is written, and an `execution_dlq` row records the stable DLQ reason `reclaim_max_attempts_exceeded`, attempts, first/last failure timestamps, retry-after, queue/run/trace metadata and replay payload context.
