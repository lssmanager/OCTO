F0 — Foundation Phase
Documento técnico definitivo

1. Executive Summary
F0 es la fase de fundación operacional mínima de OCTO y su objetivo es dejar lista la base técnica, de infraestructura y de observabilidad sobre la cual podrán construirse el runtime durable, la jerarquía agentic, los tools, la memoria y la gobernanza sin reescribir la arquitectura base.

La arquitectura oficial de OCTO define que el sistema debe crecer por capas: infraestructura primero, luego kernel durable, después jerarquía, inteligencia agentic, tools, memoria, multi‑agent orchestration, graph engine, channels, providers, observabilidad y gobierno; F0 ocupa deliberadamente la capa inicial de infraestructura y base operativa, no la de ejecución inteligente real.

F0 resuelve los siguientes problemas fundacionales:

Define el monorepo oficial, sus boundaries y el stack técnico estable para evitar drift estructural temprano.

Separa desde el día 1 Presentation, Control Plane, Orchestration, Runtime, Provider Abstraction, Persistence, Security y Observability para impedir acoplamientos que luego serían costosos de revertir.

Establece Docker, Compose, networking, env management, validación de configuración y estrategia de despliegue continuo vía Coolify como baseline operable.

Deja visibles PostgreSQL, Redis, LiteLLM, API y GUI mínima con health checks y logs, porque cada fase debe producir un sistema vivo y verificable por URL, no solo código que compila.

Arranca la disciplina de observabilidad estructurada y la separación de workers aislados por responsabilidad, lo cual la doctrina de OCTO considera no negociable desde etapas tempranas.

F0 no intenta resolver ejecución real de agentes, planning, tool calling real, memory pipelines, channels productivos, approvals durables de negocio, graph execution ni governance enterprise completa.

La propia descripción de fases de OCTO ubica la ejecución real del runtime en una fase posterior al baseline de infraestructura, y muestra para F0 un dashboard de estado donde el API, PostgreSQL, Redis y LiteLLM están online pero el runtime aparece offline.

Por diseño, F0 debe entenderse así:

F0 no es un producto funcional.

F0 es infraestructura durable y fundacional.

F0 habilita F1/F2 al congelar las interfaces, los límites de capas, la persistencia base, la observabilidad y la topología operativa.

1.2 Estado objetivo de F0
El estado correcto de cierre de F0 es un sistema desplegable con web, API, PostgreSQL, Redis y LiteLLM conectados, health checks respondiendo, networking resuelto y una GUI mínima de estado operacional que exhibe la fundación viva de OCTO.

Ese estado no incluye runtime AI funcional ni jerarquía agency/department/workspace/agent ejecutable; esos elementos pertenecen a fases posteriores del plan oficial.

2. Architectural Principles
2.1 Control Plane vs Execution Plane
La arquitectura oficial de OCTO congela una separación estricta entre Control Plane y Execution Plane.

El Control Plane vive en NestJS y es responsable de gateway API, casos de uso, gestión de jerarquía, runs, approvals, budgets, policies, flows, settings y coordinación del sistema; el Execution Plane vive en workers aislados, especialmente runtime-worker en Python/FastAPI, y es el único lugar donde puede existir el loop de ejecución AI, reasoning, planning, memory y tool loop.

La separación existe por cinco razones estructurales:

Contención de fallos: una caída del runtime no debe tumbar el API ni el frontend.

Escalado independiente: Control Plane y workers deben escalar según perfiles de carga distintos.

Aislamiento operativo: cada responsabilidad crítica debe tener proceso, contenedor y límites de recursos separados.

Seguridad: los workers AI no deben tener acceso indiscriminado a secretos globales, host filesystem ni canales críticos.

Claridad de ownership: el frontend renderiza proyecciones y el backend coordina; ninguno de los dos ejecuta lógica AI real.

2.1.1 Qué puede hacer cada plano
Plano	Permitido	Prohibido
Control Plane	API, auth base, orchestration, scheduling, state transitions, persistence coordination, health, ops, contracts	Ejecutar reasoning AI dentro del proceso API, tool loop real, lógica de runtime embebida en controllers
Execution Plane	Ejecución aislada, retries, checkpoints, telemetry runtime, recovery, workers por responsabilidad	UI logic, ownership de negocio del API, acceso lateral a otros workers, persistencia no coordinada

En F0, esta separación existe como baseline arquitectónico y como topología operativa, pero el runtime real todavía no está activo como capacidad de negocio final; el documento de fases muestra explícitamente que F0 expone “Runtime Offline”, mientras el runtime operativo real aparece en una fase posterior dedicada al execution engine.

2.2 Durable Execution Model
Aunque la ejecución durable completa pertenece a una fase posterior, F0 debe fijar desde ya el modelo semántico de durabilidad para impedir que F1/F2 tengan que reemplazar storage, colas, observabilidad o semántica de transición.

La doctrina de OCTO adopta inspiración de LangGraph y del modelo de durable execution: checkpoints, replay, retries, pause/resume, reclaim, event logging y separación estricta entre estado durable y estado en memoria.

Los componentes del modelo son los siguientes:

Leases para ownership temporal de ejecución por worker.

Heartbeats para detectar workers caídos o ejecuciones zombie.

Reclaim para retomar runs abandonados por expiración del lease.

Retries con backoff y DLQ para fallos transitorios o mensajes venenosos.

Checkpoints como snapshots persistidos del progreso de ejecución.

Idempotency para neutralizar redelivery y duplicación propia de sistemas at-least-once.

Replay safety para rehidratar ejecución sin depender de memoria local.

CAS transitions para impedir carreras entre workers o entre API y workers.

2.2.1 Guarantees de F0
F0 sí garantiza estas bases:

El estado durable debe vivir en PostgreSQL y no en memoria del worker.

La semántica deseada de runtime debe ser durable, replayable y observable antes de introducir multi-agent o UI avanzada.

Las colas y workers deben construirse con asunciones at-least-once, no exactly-once.

Todo error significativo debe emitir evento y log estructurado; no se permiten catches silenciosos.

2.2.2 Non-guarantees de F0
F0 no garantiza todavía:

Ejecución LLM real end-to-end.

Checkpoint replay funcional de negocio.

Pause/resume semántico usable por usuarios.

Recuperación operativa completa desde cualquier checkpoint.

Token/cost accounting operativo por ejecución real.

2.3 Event-Driven Architecture
OCTO define el sistema de eventos como el “tejido nervioso” del sistema, porque sin eventos no hay replay, timelines, debugging ni observabilidad consistente.

La arquitectura de F0 debe por tanto establecer una abstracción de colas sobre BullMQ, workers dedicados, write-before-ack, DLQ y payloads tipados, aun cuando parte de los consumidores de negocio todavía sean stub.

Los principios mínimos son:

BullMQ es el motor de jobs y scheduling del plano de orquestación.

Todo job debe ser tratable como at-least-once.

La confirmación del job ocurre después de persistir el estado relevante o el evento necesario, nunca antes.

Las rutas de fallo deben terminar en DLQ, no en pérdida silenciosa de mensajes.

Las colas deben exponer instrumentación, retries, backoff y trazabilidad de punta a punta.

2.4 Multi-Tenant Foundation
La arquitectura objetivo de OCTO distingue con fuerza entre jerarquía cognitiva y tenancy: Agency/Department/Workspace/Agent/SubAgent modelan topología cognitiva y operacional, no un sistema SaaS de tenants.

Esa distinción es crítica porque evita que el sistema termine modelando RBAC de SaaS donde en realidad necesita DAGs de ejecución cognitiva y autoridad delegada.

Para F0, la lectura correcta es la siguiente:

El hierarchy no pertenece a auth; pertenece a agent-core como modelo cognitivo.

F0 puede preparar propagación de tenantId en contratos, payloads y tablas críticas como foundation contract, pero no debe presentar tenancy completa como feature cerrada.

JWT, RBAC y RLS no forman parte del alcance funcional de F0; quedan diferidos a F1+ como capacidad de seguridad de aplicación y aislamiento de acceso.

2.5 Observability First
La doctrina de OCTO congela que la observabilidad existe desde F0 y nunca puede tratarse como afterthought.

Desde la fundación, cada evento y log debe portar al menos traceId, runId, agentId y executionId, porque sin esos cuatro campos el sistema se vuelve indebuggeable en producción.

La stack oficial de observabilidad es:

OpenTelemetry para trazas y contexto distribuido.

Prometheus para métricas.

Loki para logs estructurados.

Grafana para dashboards y operación.

3. Monorepo Architecture
3.1 Turborepo Strategy
El monorepo oficial de OCTO usa Turborepo y pnpm como base de build graph, caching, workspace management y pipelines reproducibles.

La razón arquitectónica es que el sistema combina frontend, API, workers, paquetes compartidos, infra y documentación bajo un único baseline versionado, y necesita boundaries explícitos para impedir dependencias circulares y acoplamientos ilegítimos.

Las reglas del build graph son:

Los paquetes base se compilan antes que las aplicaciones que los consumen.

Los contratos compartidos fluyen hacia apps y workers; nunca al revés.

Los adapters externos se encapsulan en packages dedicados y no se filtran al core.

El caché de Turbo debe acelerar lint, typecheck, build y test sin cambiar el orden lógico de dependencias.

3.3 Boundary Enforcement
F0 debe imponer boundaries de paquete porque la principal deuda temprana en sistemas de este tipo aparece cuando frontend, API, runtime y adapters comparten lógica por conveniencia.

La arquitectura oficial declara explícitamente que si una capa viola su columna “Prohibido”, el diseño es incorrecto y debe rediseñarse la interfaz entre capas, no introducir workarounds.

Reglas normativas:

apps/web no importa lógica de negocio desde workers.

apps/api no importa SDKs externos de LLM directamente; solo contratos y abstracciones.

apps/runtime-worker no importa módulos de UI ni controladores NestJS.

@octo/sdk-abstractions es el único lugar autorizado para encapsular SDKs externos o gateways de providers.

@octo/agent-core conserva la jerarquía cognitiva fuera de auth.

6. Durable Execution Internals
F0 no entrega runtime AI funcional, pero sí debe entregar el esqueleto técnico auditable del lifecycle de ejecución para que F1/F2 no tengan que redefinir semántica de colas, leases, estados o storage.

6.1 Execution lifecycle fundacional



En F0, esta secuencia debe entenderse como lifecycle model y no como afirmación de que toda la lógica de negocio ya está operativa en producción.

6.2 Lease acquisition
Pseudocódigo normativo:

text
begin tx
  load execution where id = :id
  ensure state in [PENDING, RETRY_SCHEDULED, RECLAIMABLE]
  update execution
    set lease_owner = :worker_id,
        lease_expires_at = now + lease_ttl,
        version = version + 1
    where id = :id and version = :expected_version
commit
6.3 Heartbeat refresh
text
if worker owns lease:
  periodically update lease_expires_at
  emit heartbeat metric/log
else:
  stop processing and abort local execution
6.4 Reclaim algorithm
text
scan executions where lease_expires_at < now and state = RUNNING
for each execution:
  CAS transition RUNNING -> RECLAIMABLE
  enqueue reclaim job
  new worker reacquires lease
  resume from latest durable checkpoint
La doctrina base de OCTO exige reclaim, retries, replay y pause/resume como propiedades del runtime durable inspirado por LangGraph, aunque la disponibilidad funcional completa de esas propiedades quede diferida respecto a la fundación inicial.

6.5 Race condition handling
Riesgos a tratar desde F0:

Doble dispatch por redelivery de BullMQ.

Worker antiguo intentando escribir después de perder lease.

Reclaim concurrente por múltiples scanners.

Retry y completion compitiendo entre sí.

Mitigaciones fundacionales:

CAS por version en la fila de ejecución.

Idempotency keys por job o paso.

Write-before-ack.

Abort del worker si pierde ownership observable del lease.

8. Queue & Worker Reliability
F0 debe asumir semántica at-least-once delivery, porque ese es el modelo realista de BullMQ y de sistemas distribuidos de jobs.

Por tanto, la confiabilidad no se logra evitando duplicados mágicamente, sino diseñando workers idempotentes, write-before-ack, DLQ, backoff y reconciliación periódica.

8.1 Garantías reales
Un job puede entregarse más de una vez.

Un worker puede caer después de escribir pero antes de ack.

Un scheduler puede duplicar intentos por timeout o reclaim.

Redis puede reiniciarse y requerir reconciliación desde el estado durable de PostgreSQL.

8.2 Duplicate protection
Protecciones mínimas:

Job IDs determinísticos cuando aplique.

Idempotency keys persistidas.

CAS sobre executions.version.

Event dedupe cuando el consumer sea sensible a duplicados.

8.3 Poison messages y DLQ
Un mensaje venenoso es aquel que falla repetidamente por la misma causa o por una causa no recuperable y no debe seguir ciclando indefinidamente en la cola.

F0 debe ya tener semántica de DLQ, persistencia de DLQ y visibilidad operativa sobre jobs en ese estado, aunque el playbook completo de reprocess pueda quedar para fases posteriores.

8.4 Retry backoff
La política exacta puede cambiar por tipo de job, pero la fundación debe soportar como mínimo backoff exponencial, límite de intentos y captura de error estructurada por intento.

8.5 Reconciliation loops
Debe existir o quedar claramente preparado un reconciler que compare estado durable con estado de colas para detectar:

ejecuciones sin job activo,

leases expirados,

jobs huérfanos,

transiciones intermedias no consolidadas.

11. Governance & ADRs
La filosofía de ADR en OCTO es congelar decisiones arquitectónicas estructurales para que la implementación no derive hacia workarounds, bypasses o soluciones paralelas sin estrategia de reemplazo.

El proyecto prohíbe explícitamente fixes temporales, ocultamientos de errores, bypass de capas y duplicación de lógica de negocio como solución al acoplamiento.

11.1 Restricciones arquitectónicas inmutables
El runtime no vive en frontend ni API.

Los channels son dumb adapters y nunca orquestan.

La UI renderiza proyecciones y no contiene lógica de negocio.

La observabilidad existe desde F0.

Los approvals durables no pueden modelarse como flags efímeros en memoria.

Cada deploy debe dejar el sistema igual o mejor, nunca más frágil.

11.2 ADR‑0016 y ADR‑0017
Este documento trata ADR‑0016 y ADR‑0017 como referencias normativas obligatorias del baseline F0 para decisiones congeladas de arquitectura y límites de fundación, y por tanto toda implementación de F0 debe enlazar y respetar esos ADRs en el repositorio.

12. Known Limitations of F0
12.1 Deliberately Deferred to F1+
Ejecución real de tareas por runtime-worker.

Jerarquía Agency/Department/Workspace/Agent visible, navegable y persistida como feature de producto.

Tool runtime universal y MCP operativo.

Memoria semántica, RAG y pipelines de embeddings.

Channels productivos como WhatsApp, Telegram o Discord.

Governance, approvals humanas durables, budgets completos, audit profundo y seguridad enterprise de aplicación.

JWT, RBAC, SSO, SCIM y aislamiento de acceso completo.

12.2 Technical Debt
runtime-worker existe antes de su capacidad real de negocio, por lo que parte de su superficie es contract-first o stub.

Parte del modelo durable vive como semántica congelada más que como flujo funcional completo en F0.

La presencia de LiteLLM en F0 es de wiring/plumbing, no de inferencia real productiva.

Algunos workers existen solo como placeholders para preservar boundaries correctos y evitar que la lógica futura termine mal ubicada.

12.3 Known Risks
Drift entre contratos y comportamiento real si F1 avanza sin endurecer runtime-state y queue.

Falsa sensación de completitud si se confunde “infra levantada” con “runtime funcional”.

Acoplamiento indebido entre API y runtime si se intenta acelerar F1 incrustando lógica AI en NestJS.

Subinstrumentación temprana que rompa la trazabilidad de runs cuando el sistema crezca.

12.4 Non-Goals
No entregar un producto agentic usable por usuarios finales.

No entregar multi-agent orchestration.

No entregar graph runtime visual.

No entregar canales y memory stack completos.

No entregar seguridad de aplicación completa tipo SaaS enterprise.

13. Foundation Readiness Assessment
La fundación F0 debe evaluarse por su capacidad de soportar crecimiento sin reescritura arquitectónica, no por cantidad de features visibles.

13.1 Scorecard
Dimensión	Evaluación	Justificación
Durability baseline	Alta	PostgreSQL como source of truth y semántica durable congelada.
Modularity	Alta	10 capas, workers aislados, monorepo con boundaries.
Extensibility	Alta	packages/contracts, sdk-abstractions, workers reservados, deployment base.

13.2 Juicio arquitectónico
F0 está listo cuando evita reescritura de capas base en F1, no cuando ya “parece un producto”.

Si F1 necesita mover runtime al API, rehacer storage, cambiar el modelo de colas, redefinir contratos o añadir observabilidad desde cero, entonces F0 no estuvo realmente cerrado.

15. Appendix
15.1 Glossary
Control Plane: plano NestJS que coordina, expone API y gobierna estado.

Execution Plane: plano de workers aislados que ejecuta runtime y tareas especializadas.

Lease: ownership temporal de una ejecución por un worker.

Heartbeat: señal periódica de vida y progreso operativo.

Reclaim: reasignación de una ejecución abandonada o zombie a otro worker.

CAS: compare-and-swap por versión para transiciones optimistas.

DLQ: dead-letter queue para jobs no recuperables o poison messages.

Write-before-ack: persistir primero, reconocer el job después.

Foundation Critical: elemento que no puede cambiarse sin dañar F1+.

Este documento define F0 como baseline estable, auditable y deliberadamente limitado: monorepo, infraestructura, contracts, persistence base, queue plumbing, observabilidad, seguridad de contenedor y topología operativa correcta; no define todavía un runtime AI funcional ni una plataforma agentic completa.
